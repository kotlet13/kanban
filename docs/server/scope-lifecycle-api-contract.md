# Scope lifecycle contract1 (FamilyHub0.14 / schema18)

Current source distribution: **FamilyHub 0.15.0 / schema19**. Existing wire/contract identifiers below keep their original versions. Organization tables and private attachments are specified in the bundled `DOCUMENTS_API.md`; current distribution source is distinct from hosted deployment evidence.

Capabilities advertise `scopeLifecycleContractVersions:[1]` and features `scopeDeletion` / `scopeArchiving`. Authenticated requests use the existing Native API bearer. These operations never delete an account or device registration.

`scopes.deletionPreview` accepts `{scopeId,projectId?}`. Its named preview includes selected child spaces, counts of spaces/projects/tasks/events/ideas/photos/finance/other, `canDelete`, explicit `blockers`, and `previewHash`. A whole household, organization or project scope requires its owner. An inline project accepts existing nonviewer editors; selected finance additionally requires existing financial write access. Deleting the permanent root project means deleting its project scope and requires ownership. Whole personal-space deletion is excluded.

After explicitly displaying and confirming that preview, `scopes.delete` accepts `{scopeId,projectId?,previewHash,requestId}` with a fresh UUID request ID. A changed graph returns `scope_deletion_preview_changed`; blockers return `scope_deletion_blocked`. Preserve the exact approved body and request ID across uncertain responses and restarts. Exact replay returns the prior receipt, including after deletion. Do not silently approve a newer preview.

Whole-scope deletion includes its descendant scopes and content. A descendant owned by someone else blocks deletion until ownership is resolved. Inline project deletion removes its tasks, events, idea boards/photos and project- or task-linked finance entries, while retaining unrelated household ledger accounts and records. External linked-payment projections, cash or reimbursement references block the graph rather than deleting facts in another scope. Parents, sibling scopes and unrelated accounts remain intact.

Deletion is transactional. Scope identities remain as permanent `deleted_at` markers; content remains only as payload-null revision/sequence tombstones. Prior operation response snapshots are scrubbed while request hashes remain. Old queued writes cannot resurrect the graph. Invitations and pending reminders are canceled; inbox/delivery references and selected moderation evidence are removed/redacted. `scopes.list` with `includeAccessChanges` includes `deletedScopeIds` so historical offline replicas can hide deleted scopes. Owner replay remains available, ordinary access returns `scope_deleted`.

Private image metadata is deleted in the transaction, with a durable file-cleanup queue. File unlink occurs only after commit and retries through the existing idea cleanup invoked by the reminders worker. A deletion receipt with `cleanupPending:true` means physical cleanup may still be pending; protect and monitor the server's private data directory and cleanup worker. Protected server backups and previously downloaded/exported copies are outside this operation.

`scopes.archive` accepts the existing `{scopeId,archived,requestId}` contract for household, organization and project scopes. Archived scopes retain records and membership; parent archive also blocks descendant normal writes, invitations/acceptance and delivery. Inline archived project records require record6, guard task/event/idea/finance edits, and allow explicit restore. Due reminders skipped during archive are canceled on restoration rather than replayed. Archival does not grant new access.

Normal removal from a household or organization also removes that person's separate direct memberships/grants and pending invitations throughout its descendants. Ownership of a child project must be transferred first (`project_owner_transfer_required`); rejection leaves all memberships unchanged. Moderation restriction/reversal remains a distinct reversible process. Revoked clients hide authorized live projections, retain their own immutable unsent drafts/operations for recovery/export and cancel active local reminders; they do not claim to recall already downloaded copies.

Upgrade schema17 to18 only after a verified full database/private-file/configuration backup and restore rehearsal. The migration is additive and idempotent. Replacing code alone with pre18 code is not a safe rollback: restore the verified backup under a coordinated worker pause instead.
