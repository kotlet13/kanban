# Deljenje celotnega prostora in posameznega projekta (policy3)

Current source distribution: **FamilyHub 0.15.0 / schema19**. Existing wire/contract identifiers below keep their original versions. Organization tables and private attachments are specified in the bundled `DOCUMENTS_API.md`; current distribution source is distinct from hosted deployment evidence.

Izvor FamilyHub 0.11.0/schema15; namestitev je ločen korak. Kanboardove skrbniške pravice se ne spreminjajo. Finance2 in linked-payment3 ohranita svoje metode, telesa in identitete operacij.

## Pogodba dostopa

`spaceAccessPolicyVersions:[3]`, `organizationAccessPolicyVersions:[1,2,3]`, `invitationContractVersions:[1,2,3]`; zmožnosti `spaceProjectMembership`, `scopedInvitations`, `projectSharingMigration`.

Policy3 sprejeto članstvo v household/organization daje vse skupne vsebine, finance ter obstoječe in prihodnje projektne otroke. Sprejeto članstvo v project daje samo ta projekt. `member` lahko bere, ustvarja, ureja in odstranjuje vsebino, skupne finance, povabila, članstvo ter nastavitve znotraj svojega cilja. `viewer` ostane samo branje. `owner` ostane dejanski edini lastnik; odstranjevanje lastnika je prepovedano. Sprememba lastništva/izbris računa zahtevata obstoječi preverjen postopek. Osebni prostori ter zasebni računi se ne dedujejo.

Scope wire dodaja `parentScopeId` (nullable UUID), `parentScopeKind` (nullable household/organization), `accessSource` direct/spaceMembership/leadership. `organizationId` ostane alias samo organizacijskega starša. Projekt ima en `projectRootId`; podedovani owner je v tujem projektnem otroku `member`. Pravice neposrednega in podedovanega članstva se združijo; preklic starša ne prekliče posebej sprejetega projektnega članstva.

`scopes.create` sprejme `accessPolicyVersion:3` za novi household/organization/project in `parentScopeId` za novi projekt; podeduje politiko starša. `projectPayload` je ista record3 pogodba. `scopes.members` policy3 vrne učinkovito unijo s `accessSource`, `membershipScopeId`, `accessSources` ter `inheritedFromScopeId`. Odstranitev iz otroka odstrani samo neposredno članstvo; podedovane pravice ostanejo.

## Povabila3

`invitations3.create`: `{scopeId, recipientEmail, role, requestId, language, accessScope, expiresIn?}`. `accessScope` je obvezno `space` za household/organization ali `project` za project; ciljni scope mora uporabljati policy3. `role` member/viewer, language sl/en. Vrne `{invitation,deliveryQueued:true}`; žeton fhi3_ je samo v šifrirani poštni vrsti/povezavi. Wire invitation ima `contractVersion:3`, `accessScope`, `sharedFinanceIncluded:true` in stare identifikatorje/podatke prejemnika ter roke.

`invitations3.preview:{token}`, `invitations3.pending:{}`, `invitations3.accept:{token}` ali `{invitationId}` ohranijo email2 identiteto in ločen izrecni sprejem. Registracija (`auth.registerInvitation3`) nikoli ne dodeli članstva; prijava prav tako ne. List/revoke uporabljata obstoječi `invitations.list/revoke`, ki vrneta/verificirata shranjeno verzijo. Stara create1/2 za policy3 vrneta `client_upgrade_required`.

### Source supplement - 16 October 2026

The initial local invitation implementation made no release/version bump, schema change or live hosting change. The current combined source distribution is0.15.0/schema19. New feature flags `usernameInvitations` and `invitationResend` independently advertise the additions below. Missing flags on an older server mean unsupported. Both are independent of SMTP; email creation/resend still requires `emailInvitations:true`.

`invitations3.create` accepts `recipient` as an alternative to compatible `recipientEmail`: **exactly one** field must be present. A `recipient` containing `@` follows the existing verified-email contract. Otherwise it is the exact existing active username with a Native account on this server, normalized with the same trim/lowercase rules as login. No account is created, no membership granted, and the legacy username invitation/registration path is not used. `recipient_unavailable`409 covers absent/inactive/non-Native/self targets; malformed syntax is `validation_error`. There is no unauthenticated directory. Authenticated scoped discovery is described in the 27 October supplement below. Current scope-management ACL, separate content policy acceptance and quotas apply before invitation target resolution.

A username invitation binds durable `recipient_account_id` and stores `recipient_email:null`. The response has the normalized submitted `recipientUsername`; it never discloses a hidden or verified email address or target account ID. `deliveryQueued:false` means an invitation waiting in the recipient account, **not sent email**. No token is returned and no mail job created. `invitations3.pending` returns it only to the bound account, even with no verified email/SMTP; the recipient explicitly joins using `invitations3.accept:{invitationId}`. Renaming/reusing a username cannot transfer an existing invitation to another account. Removing or deleting an account with a reused username also cannot revoke/purge invitations bound to the original account; username-based cleanup remains restricted to legacy contracts. Registration3 is refused for username invitations; any token preview has `registrationAllowed:false`. The email channel and legacy contracts retain their existing identity and registration semantics.

`invitations3.resend:{scopeId,invitationId,requestId,language,expiresIn?}` accepts a nonaccepted/nonrevoked invitation3, including expired ones. It requires current scope-management access and accepted content policy. One transaction returns `{invitation,deliveryQueued}` with a **new ID, random token and expiry** (default24h, allowed60-604800s) for the same recipient, role and access scope. It revokes the original and cancels/clears any undispatched old mail ciphertext. A queue/storage failure leaves the original unchanged; the client never performs a separate revoke. An accepted original returns `invitation_already_accepted`409; revoked/wrong scope/wrong ID/legacy contract returns `invitation_invalid`404. The exact requestId/body replays the same successor; changed bodies return `idempotency_mismatch`409. Concurrent distinct resend requests produce one successor. Already SMTP-accepted old mail cannot be recalled, but its old invitation link no longer works.

Create and resend share sender30/day, normalized recipient5/day and IP120/minute quotas; retries count. Username invitations never send mail to `users.email` or an implicitly resolved verified address. All fields already exist; there is no DDL/migration.

### Source supplement - 27 October 2026: recipient search

`features.recipientSearch:true`, together with `usernameInvitations:true`, advertises `recipients.search:{scopeId,query}`. This authenticated metadata read requires current policy3 invitation-management access to the exact nonpersonal, nonarchived scope; encrypted scopes also use their current management guard. The query is trimmed, 2–64 UTF-8 characters, and matches a literal substring of username or display name. Email queries and control characters are rejected. SQL `%`, `_` and the escape character remain literal. SQLite folds display names with a dedicated per-connection UTF-8 function used only by this query; MySQL uses its normal `LOWER`. No schema change is required.

The response is `{recipients:[{accountId,username,displayName}]}` with at most ten deterministic results, restricted to other active initialized Native accounts that can use local login. Inactive, deleted, LDAP-only, login-disabled and self accounts are excluded. Neither email addresses, email verification state, membership lists nor arbitrary account fields are returned. Quotas are 60 searches/account/minute and 120/IP/minute. Search never creates accounts, invitations, memberships or encrypted grants.

The invitation form debounces for 350 ms, searches from two characters, ignores obsolete responses after text/session/scope changes, and fills the selected exact username. Selection also supplies optional `recipientAccountId` to `invitations3.create`; server-side resolution must still match that account or returns `recipient_unavailable`. The encrypted client checks the same binding against freshly resolved recipients and retained immutable invitation drafts before signing/sending. The selected account participates in the form's retry identity. Existing consent, explicit recipient acceptance, signed commands, encryption grants and pending requests retain their guards.

A missing capability keeps the exact username/email form and its existing wire body. Typing an exact username or email without selecting a suggestion also retains the compatible invitation contract; a failed search leaves the input available. Exact email invitation delivery still depends on the advertised email capability and its existing verified-email rules. This supplement describes local source only; no hosting deployment or phone installation is implied. New targeted evidence is under `build/qa/recipient-search-20261027/`; tests cover synthetic transport, headless widgets and real native dispatch on fresh memory SQLite, without HTTP or a full signed crypto invitation round trip.

## Izrecna nadgradnja obstoječega prostora

`scopes.accessMigrationPreview:{scopeId,targetVersion:3}` in `scopes.accessMigrationApply:{scopeId,targetVersion:3,previewHash,requestId}` sta dovoljeni dejanskemu lastniku household/organization oziroma samostojnega project prostora. Projektni otrok nadgrajuje politiko prek svojega starša. Samostojni legacy project potrebuje natanko en živ projekt record3 ter vse task/event vezane nanj; sicer `canApply:false` in `project_scope_requires_single_root`, `project_record_upgrade_required` ali `project_scope_unrelated_content`. Spremembe tega grafa spremenijo previewHash. Opuščeni targetVersion ohrani prejšnjo nadgradnjo na2 za organization.

Preview: `{scopeId,fromVersion,toVersion:3,canApply,blockers,projects:[{scopeId,name,financeWasEnabled,additionalReaders:[{accountId,displayName,accessSource}],additionalWriters:[...]}],revokedInvitationIds,previewHash}`. `projects` vključuje tudi sam korenski prostor. Hash pokriva članstva, finančno politiko/grante, projekte in čakajoča povabila. Apply vrne `{scope,preview}` in trajno ponovi isto telo pri izgubljenem odgovoru. Nadgradnja omogoči skupne finance ter prekliče vsa še nesprejeta stara povabila v korenu in otrocih; starih ne razširi tiho. Učinkovita politika3 se shrani tudi na otrocih; ob ločitvi zaradi potrjenega izbrisa starša ostane3. Stari target2 ne sme nadgradnje obrniti in vrne `client_upgrade_required`.

## Izločitev starega gospodinjskega inline projekta

`scopes.projectSharingPreview:{scopeId,projectId}`; `scopeId` je household policy3. `scopes.projectSharingApply:{scopeId,projectId,previewHash,requestId}`. Člani lahko opravijo izločitev.

Preview: `{scopeId,projectId,projectName,canApply,blockers:[{code,recordId?}],movedRecordIds,movedFinanceRecordIds,movedReminderIds,financeAccounts:[{id,name,currency,openingBalanceMinor,openingBalanceAt}],householdPeople:[{id,name,notes}],previewHash}`. Apply: `{scope,projectRoot,movedRecordIds,movedFinanceRecordIds,movedReminderIds}`. Novi child scope ima ID enak izvirnemu projectId; vsi domeni ID-ji/revizije izločenega grafa se ohranijo. Povezane finance so financeEntry s taskId projekta, njihovi izključno uporabljeni računi/pravila ter izključno uporabljeni profili oseb. Oseb ni tiho podvojenih. Predogled pokaže tudi prenesena začetna stanja računov in zapiske oseb. Prenos med dvema že izbranima izključnima projektnima računoma se preseli z istim ID-jem; prenos v račun zunaj grafa je blocker. Zaradi morebitnega enakega UUID-ja v splošni in finančni tabeli se obvestila/opomniki preselijo samo ob ujemanju ID-ja in vrste zapisa. Obvestila in opomniki sledijo svojemu premaknjenemu cilju.

Izločitev zavrne ponovno uporabljeni gospodinjski račun (`project_finance_account_shared`), pravilo (`project_recurrence_shared`), profil (`project_person_shared`), medobsežni prenos (`project_transfer_cross_scope`), povezano plačilo (`project_linked_payment_dependency`), ID kolizijo (`project_scope_id_collision`) ali preskromen projektni format (`project_record_upgrade_required`). Izločitev zato nikoli ne kopira preostalega gospodinjstva ali opening balance drugega projekta. Uporabnik mora ločiti skupno odvisnost pred ponovnim predogledom.

Apply je atomaren pod ključavnico gospodinjstva. Izvor dobi tombstone in evidenco selitve; novi zapis v starem obsegu vrne `record_relocated`, predhodni idempotentni odgovor pa ostane ponovljiv. Stari neizločeni projekti ostanejo dostopni. Odjemalec pred apply preveri lokalne čakalne vrste/konflikte in ob negotovem odgovoru zaklene spreminjanje izvornega obsega do ponovitve zahteve; teles ali ID-jev starih operacij ne prepisuje. Zastarel preview vrne `project_sharing_preview_changed`; neizločljiv graf `project_sharing_blocked` z blockerji.
